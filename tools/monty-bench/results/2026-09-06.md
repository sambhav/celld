# Monty is worth an integration experiment, not an interpreter rewrite

The native Rust/Monty prototype reaches roughly celld TypeScript throughput at
four execution threads with much lower process memory. This supports a bounded
optional-backend experiment alongside Pyodide. It does **not** establish that
Monty integrated into celld will retain that throughput, or that Monty's Python
execution is intrinsically faster. No Monty fork or production backend was added.

[Successful GitHub run](https://github.com/sambhav/celld/actions/runs/34026633444),
benchmark source `43ea09de9b56a866ccd771812d9872a85df01c9d`, Monty source
`af272c3116e2525249103f960b79086fd250bcef`, Rust 1.98.1, AMD EPYC 7763, two physical
cores/four logical CPUs. Three five-second rounds, 256 concurrent clients,
72 samples, **3,381,435 measured responses, zero errors**. Upstream request and
completion counts match every I/O sample exactly. Backend order rotates between
rounds. Raw samples and executable hashes: [2026-09-06.json](2026-09-06.json).

## HTTP results

These backends have intentionally different hosts:

- Python and TypeScript run through the same actual celld binary, source
  `37e41ff2dcd6e1097f4207406a6b5a63a8e647fc`. Python includes the new scheduler and
  response-adapter optimizations and keeps default JSPI support.
- Monty runs in a separate fixed-code axum executable with a native Rust
  interpreter. Rust awaits real reqwest HTTP while the interpreter is suspended,
  then resumes Python to validate and transform the returned JSON. Each request
  gets a fresh heap from a cached compiled program. The worker includes a typed
  function and identity decorator, not the celld SDK or Pydantic validation.
- Rust is the same axum/reqwest executable with Rust business logic. It estimates
  the remaining host/driver/upstream ceiling of this setup.

Median requests/second:

| Execution slots | Workload | celld Python | celld TypeScript | Native Monty prototype | Rust control |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | JSON hello | 2,122 | 12,039 | 8,747 | 36,785 |
| 4 | JSON hello | 5,001 | 19,356 | 20,342 | 41,722 |
| 1 | Real HTTP I/O, 10 ms | 927 | 3,874 | 3,206 | 8,333 |
| 4 | Real HTTP I/O, 10 ms | 2,183 | 7,642 | 7,558 | 15,065 |
| 1 | Real HTTP I/O, 50 ms | 930 | 3,851 | 3,307 | 4,924 |
| 4 | Real HTTP I/O, 50 ms | 2,121 | 4,730 | 4,778 | 4,888 |

Execution slots mean Tokio worker threads for Monty/Rust and maximum stateless
isolate counts for celld; those mechanisms are not interchangeable. Monty is
slower than TypeScript in all three one-slot cases. Four-slot throughput is
within about 5% of TypeScript, but hello p95 is slightly worse (29.54 versus
27.80 ms). I/O 10 ms p95 is 47.82 versus 46.81 ms; I/O 50 ms 56.35 versus 57.45 ms.
This is feasibility evidence, not a statistical equivalence test.

Monty scales 2.33x on hello and 2.36x on I/O 10 ms from one to four threads,
not linearly on this two-core machine. The 50 ms case is close to its closed-loop
ceiling: 256 clients / 0.05 seconds = 5,120 req/s even before other costs.

## Startup and memory

Four-slot medians, hello workload:

| Metric | celld Python | celld TypeScript | Monty prototype | Rust control |
| --- | ---: | ---: | ---: | ---: |
| First request after health | 711.81 ms | 1.40 ms | 1.17 ms | 0.45 ms |
| Process RSS after load | 999.9 MiB | 176.5 MiB | 19.6 MiB | 12.8 MiB |

Monty RSS is about 45 MiB in the I/O cases versus approximately 987–1,063 MiB
for celld Python. This compares whole processes with different responsibilities;
it is not a measurement of memory savings after embedding Monty in celld.

The prototype reaches health in about 11 ms, quantized by a 10 ms polling loop.
Celld readiness is separately recorded and ranges around 1–4 seconds in these
runs. Python's first request then initializes its interpreter. These results
use fresh processes with warm disk/artifact caches. They do **not** measure
remote S3 downloads, an idle scale-to-zero eviction/wake cycle, or deployment
rollout latency. A compiled Monty template stays warm in the prototype even
though each invocation's Python heap is discarded.

## Is the interpreter itself faster?

The measurements do not establish that. Interpreter probes in the same GitHub
job, with the same hello JSON business logic:

| Path | Time per operation |
| --- | ---: |
| Warm V8 JavaScript JSON function | 0.50 µs |
| Warm native CPython 3.12 function | 3.63 µs |
| Warm Pyodide CPython 3.14 function, called in a Python loop | 6.25 µs |
| Warm Pyodide function, called from JavaScript | 8.08 µs |
| Monty cached program, new heap and module execution | 42.01 µs |
| Monty cached program clone and suspendable start | 45.52 µs |
| Monty parse and compile | 61.59 µs |
| Monty snapshot deserialization | 9.97 µs |

The Monty invocation paths include new heap creation, imports and function
setup, while the Python/V8 measurements reuse initialized functions. They are
**different lifecycle costs**, not a bytecode engine speed ranking. Monty's
warm REPL function-call API failed on this fixture, so no comparable warm-heap
Monty number is reported. Full probe output: [2026-09-06-micro.json](2026-09-06-micro.json).
The first uncached Monty compile and run were 334 and 411 µs respectively.
The initialized-app snapshot was 2,976 bytes; deserialization was timed without
claiming successful subsequent app invocation through the failing REPL API.

The Pyodide microprobe uses stock Pyodide in Node without JSPI, not celld's
snapshot/async host. Its standalone boot took 2.10 seconds. Microloops exclude
HTTP, scheduling, Pydantic, celld routing and most FFI work present in a real
worker. Nevertheless, the small warm Python function cost is evidence against
assuming that all end-to-end overhead comes from Python bytecode execution.
Profiling the actual host path is still required to attribute that overhead.

## Compatibility and correctness

Observed against the pinned interpreter:

| Feature | Outcome |
| --- | --- |
| Function decorator and annotation syntax | Passed; this does not imply annotation validation |
| Dataclass construction | Passed |
| Pending async host future and correlated resume | Passed |
| Mutable counter snapshot, restore, continue | Passed |
| Pydantic, NumPy, inspect imports | ModuleNotFoundError |
| Function `__name__` | AttributeError |
| `asyncio.sleep` | AttributeError |
| Warm REPL call to the full hello handler | NameError for `<global 4>` at `isinstance(name, str)` |

The REPL failure is preserved verbatim in the raw probe report; it occurs even
after warming the function with a feed. It needs an upstream fix or a supported
invocation strategy before relying on that API. Fresh-program invocations used
by the HTTP prototype passed throughout the load test. Separate host-adapter
tests verify fresh mutable state, out-of-order overlapping resumes, and rejection
of malformed upstream values including boolean prices; all three pass locally.
The real HTTP benchmark also rejects empty names before its timed load.

Monty's [pinned module documentation](https://github.com/pydantic/monty/blob/af272c3116e2525249103f960b79086fd250bcef/docs/limitations/modules.md)
describes a fixed built-in module set, without site-packages. Pyodide wheels
cannot simply be imported: CPython extension wheels require the CPython C API,
object model and loader. A WASM binary by itself is not that interface. A host
could expose coarse library operations through external functions, potentially
served by Pyodide, but that bridge and its performance were not implemented or
measured here. Loading Pyodide for such calls would also restore its memory and
startup costs. Retain Pyodide for rich Python/Pydantic/WASM-package applications.

## Engineering decision

1. Keep the measured Pyodide improvements: the scheduler gained 11–21% in its
   repeated A/B, and the response adapter another 8–17% in a separate repeated
   A/B. Do not multiply those gains across different runners. The async-only
   experiment's small gain does not justify losing synchronous I/O by default.
2. Pursue a bounded Monty integration spike, not a new interpreter. The strongest
   evidence is small invocation state and low startup/memory, with promising
   overall throughput despite a slower fresh-invocation microbenchmark.
3. Benchmark an actual celld-hosted Monty worker before promising parity. A Rust
   WASM worker could reuse celld's existing isolate/lifecycle boundary; the
   alternative native subprocess pool needs a host integration. Neither has
   been measured. Monty's existing WASI runtime is not automatically a
   workers-rs/wasm-bindgen worker.
4. Preserve the decorator/function API, but make the backend choice explicit
   and reject unsupported imports at build time. Pydantic and the existing SDK
   cannot be advertised as working on Monty. Static metadata generation could
   avoid missing reflection APIs; it would not reproduce arbitrary Pydantic
   validators or Python middleware semantics automatically.
5. Measure a narrower Pyodide function-call adapter on celld as another candidate.
   The microprobe and successful response A/B suggest substantial host/adapter
   work remains; they do not quantify how much a new adapter would recover.

No new external service is needed by this prototype, and no server dependency
was added to celld. Future code/state artifacts can use the existing bucket;
that storage/lifecycle integration is not implemented here. Production native
hosting must address crash isolation: Monty's [Rust guide](https://github.com/pydantic/monty/blob/af272c3116e2525249103f960b79086fd250bcef/docs/quickstart/rust.md)
recommends its subprocess pool for untrusted code. The fixed-code experiment
has an execution deadline and one allowlisted host call, but does not install
a global memory-budget allocator or a process isolation boundary.
